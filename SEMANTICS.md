# IdentityOps Semantics

This document gives the exact meaning of every declaration and operation in the
reference interpreter. [SPEC.md](./SPEC.md) says what the language is for.

The Lean files in [`SE/IdentityOps/`](./SE/IdentityOps/) state the intended meaning
formally for one regime and one carrier. The Python interpreter in
[`src/se_identity_ops/`](./src/se_identity_ops/) implements it for programs with
declarations and data. Section [Correspondence](#correspondence) says what is and
is not checked between them.

## Reused Definitions

IdentityOps does not define a theory of identity. It reuses:

- From `se-theory-persistence`, imported by the Lean files: `Generated` (the
  equivalence relation generated by asserted pairs), `Consistent`, `Admissible`,
  `Required`, `Forbidden`, `Undetermined`, `Extend`, and the operator
  classification (`none` is inapplicable; `ign`, `prs`, `brk` otherwise).
- From `se-theory-operational-identity`, adapted and not imported (the repository has
  no release tag to pin): `Faithful` and divergence witnesses. Adaptation is
  recorded in the Lean docstring of `Faithful`.

Deliberately excluded: Neutral Substrate, Individuation, and Coreference. None of
them is needed for the three experiments. The excluded constructs are listed in
[DECISIONS.md](./DECISIONS.md).

## Model

### Items and carriers

An item is a record name. A carrier is a finite list of distinct item names. There
is no referent type and no map from records to referents.

### Commitments

For each regime, the commitments in a state are:

- **P (same-commitments)**: pairs joined by (a) the regime's key column, when the
  regime is a key regime and both items have the same non-empty value, (b) a
  recorded `same` judgment under the regime, and (c) a licensed step under the
  regime.
- **D (distinct-commitments)**: pairs recorded by a `distinct` judgment under the
  regime. Nothing else is ever treated as distinct.

The **classes** of a regime are the equivalence classes of `Generated P`. Every
item is in exactly one class; an item related to nothing is in a class by itself.

### Status of a pair

For items `x`, `y` and a regime:

- **inconsistent**: some pair in D has both endpoints in one class. Statuses below
  are defined only for consistent commitments, so none is reported.
- **required**: `x` and `y` are in one class.
- **forbidden**: they are in different classes, and some pair in D has its
  endpoints in exactly those two classes. Identifying `x` and `y` would identify a
  pair asserted distinct.
- **undetermined**: otherwise. Some admissible identity relation identifies them and
  some separates them. Not required is not distinct.

These agree with Persistence's definitions through the admissible-relation reading
(`status_required_iff_all_admissible` and `status_forbidden_iff_all_admissible` in
Lean). The Python code computes them by closure; the tests compare it with an
exhaustive enumeration of admissible relations on carriers of 3 to 6 items.

### State and snapshots

A state is immutable. It holds the judgments in recording order, the applied steps
in application order, and a log of (label, outcome word) for `judge` and `apply`.

`judge` and `apply` each create a new snapshot whose index is one greater than the
last. `propose`, `check`, and `explain` create none. The initial snapshot is 0.
Earlier snapshots are never modified.

## Declarations

Declarations bind names. They never change state.

- **source**: reads the file named by `file` relative to the program, computes its
  SHA-256, and stops the run if it differs from `sha256`. The first row names the
  columns. Values are kept as text, unmodified.
- **carrier from SOURCE key "C"**: the items are the values of column `C`, in row
  order. A repeated value stops the run.
- **carrier items ...**: the items as listed. No source.
- **regime ... by "C"**: key regime on a source-backed carrier, with key column `C`.
  An empty key places the item in no class.
- **regime ... explicit**: no key; commitments come only from judgments and steps.
- **surface** and **probe**: the observed value of an item is the text in the named
  column of its row. A surface and a probe differ in role only: a surface is an
  implementation mechanism whose output determines treatment; a probe is a
  read-only observation of implementation output. They share one computation; a
  `faithful` witness is called a *divergence* for a surface and an *incoherence*
  for a probe. Whether the two roles should be separated further is open
  (see [DOUBTS.md](./DOUBTS.md)).
- **operator ... classified K under R**: `K` is `prs`, `brk`, `ign`, or `na`. It is
  relative to regime `R`. A `propose` under another regime is rejected by the
  checker, so the interpreter never chooses between regimes.

## Operations

Every operation returns an outcome (`established`, `refuted`, or `undetermined`),
a word, counts, and an explanation.

### judge

`judge L same|distinct X Y under R [from S] [scope "T"]` appends a judgment. It is
always recorded. Its outcome is read against the commitments before it:

- If the commitments before it were already inconsistent: `undetermined`,
  `recorded_in_inconsistent_state`.
- If it contradicts them (a `same` judgment on a forbidden pair, or a `distinct`
  judgment on a required pair): `refuted`, `conflicting`. The judgment is marked
  conflicting. The commitments are now inconsistent and every status query says
  so. Neither side is dropped.
- If it only restates them (`same` on a required pair, `distinct` on a forbidden
  pair): `established`, `redundant`.
- Otherwise: `established`, `recorded`.

A judgment with no `from` source is recorded, and its explanation says "no source".

### propose

`propose L O X -> Y under R` records a proposal and returns `established`,
`proposed`. It changes no state and creates no snapshot. A proposal is not a claim
that the step happened.

### apply

`apply L P` applies proposal `P` to the model state. Let `K` be the classification
of its operator.

- `na`: `undetermined`, `inapplicable`. The step is not executed. Limitation:
  inapplicability.
- `ign`: `undetermined`, `ignoring`. The step is recorded in the step log with
  `licensed = false` and joins no pair. Limitation: operator underdetermination.
  The classification alone neither licenses nor breaks continuation.
- `brk`: `refuted`, `broken`. The step is recorded with `licensed = false` and joins
  no pair. Breaking does not assert that the two items are distinct, so their
  status afterwards is whatever the other commitments make it.
- `prs`:
  - if the commitments are inconsistent: `undetermined`, `state_inconsistent`; no step;
  - else if the pair is forbidden: `refuted`, `blocked`; no step; the explanation
    names the distinct judgment and the chains that make it apply;
  - else: `established`, `licensed`. The step is recorded with `licensed = true`
    and the pair is added to P. If the pair was already required the step is still
    recorded and the explanation says so.

Every `apply` creates a snapshot, including a blocked or inapplicable one, so the
log records the attempt.

**What apply means.** `apply` changes a model of declared commitments. It does not
decide that two records or referents in the world are the same, and a `licensed`
outcome says only that the declared operator classification and the recorded
distinctions allow the model to carry the step as a continuation.

### check

All checks are read-only. A check is **warranted** when its regime names a source
and the regime's commitments are consistent. An unwarranted check returns
`undetermined`, `unwarranted`, with limitation insufficient information, whatever
its counts are. The counts are still reported.

**faithful R against S.** Let the first item of each class of `R` (in carrier order)
be its anchor. An item is *divergent* when its value under `S` differs from its
class anchor's value. A class is *divergent* when it has a divergent item. The
declared relation never splits under the treatment relation (equal values) exactly
when no class is divergent; since equal value is an equivalence, comparing with the
anchor suffices (`faithful_generated_iff_generators`). Outcomes when warranted:
`established`, `satisfied`; or `refuted`, `violated` with a witness listing up to
20 divergent classes, each with the two items, their values, and the chain of
same-commitments that relates them. Counts: items, related classes (classes with
at least two items), divergent classes, divergent items.

**collisions S against R.** Group items by value under `S`. A *merging group* has at
least two items. It is *required* when all its items lie in one class of `R`, and
*cross-class* when they lie in two or more. For each cross-class group, with `k`
distinct classes, `k(k-1)/2` class pairs are counted (summed over groups, so a
class pair that meets in two groups is counted twice). A class pair is *forbidden*
when some distinct judgment has its endpoints in those two classes. Outcomes when
warranted:

- some forbidden class pair: `refuted`, `contradicted`;
- else some cross-class group: `undetermined`, `unsupported`. The surface treats
  these items the same and the criterion neither requires nor forbids it. This is a
  commitment of the surface that the criterion does not support. It is not a
  claim that the surface is wrong;
- else: `established`, `supported`.

The explanation lists up to 20 cross-class groups (value, number of classes, one
item from each of two classes, and their key values when the regime has a key).

**consistent R.** `established`, `consistent` when no pair in D has both endpoints
in one class (vacuously true when D is empty, and the explanation says so);
`refuted`, `inconsistent` with the offending distinct judgment and the chain that
joins its endpoints.

**coverage R.** An item is *silent* when it has no key value and appears in no
same-commitment. `established`, `complete` when none is silent; otherwise
`undetermined`, `partial`, with the silent items (up to 20). Silent items are
unanchored, not distinct.

**status X Y under R.** `required` is `established` with the chain of same-commitments;
`forbidden` is `refuted` with the forbidding judgment and two chains; `undetermined`
is `undetermined` with limitation insufficient information; an inconsistent state
is `undetermined`, `inconsistent`, with the conflict.

### explain

`explain L` returns the explanation produced with the operation labeled `L`:

- **derivation**: a chain of steps `(first, second, ground, detail, source)` where
  `ground` is `key` (shared criterion value), `judgment`, or `step`;
- **witness**: fields naming what fails, plus supporting chains;
- **limitation**: a cause from the closed set (insufficient information,
  inapplicability, operator underdetermination) and, where useful, example fields.

Every explanation lists the declarations and sources it used and the number of
further witnesses omitted. Chains are shortest chains found by a fixed search, with
a fixed tie order, so the same program gives the same chain.

## Order

Program meaning depends on statement order only through `judge` and `apply`.
`propose`, `check`, and `explain` are functions of the current state, and inserting
them anywhere does not change what `judge` and `apply` do. This is tested.

Independent operations are not assumed to commute. The tests show:

- `same` judgments on disjoint pairs commute: same classes, same outcomes.
- `apply` and `judge distinct` on the same pair do not: applying first licenses the
  step and the later judgment is `conflicting`; judging first blocks the step.
  The Lean theorem `licensing_order_matters` states this.
- Two `apply` steps that jointly would join a distinct pair do not commute: which
  one is licensed depends on order.
- Over all orders of four operations, more than one outcome occurs.

## Determinism

Output depends only on the program text and the verified source files. Item order is
carrier order. Examples are ordered by first position. Search order is fixed. No
clock, random number, or environment variable is read. Serialized results are
byte-identical across runs, hash seeds, and working directories; this is tested.

## Correspondence

The Lean development is not a proof about the Python code. The following
obligation is stated and only partly checked.

**Obligation.** For every program over a finite carrier, the interpreter's final
same-classes, distinct-commitments, applied-step list, and pair statuses equal those
of `run` in `SE/IdentityOps/Semantics.lean` on the corresponding commands.

What checks it:

- Pair statuses: an exhaustive comparison with an enumeration of admissible
  relations on all assignments for 3 and 4 items, and a fixed sample for 5 and 6
  (`tests/test_oracle.py`), and the interpreter run end to end for 3 items.
- Command effects: `tests/test_interpreter.py` and `tests/test_order.py` check each
  case of `apply` and `judge`, and the order dependence, against the Lean statements.
- Agreement with an independent encoding: the LACE-style clingo encodings in
  [`lace/`](./lace/) reproduce the statuses on all assignments for 3 and 4 items.

What it does not cover:

- Programs larger than the cases above. The Chicago-scale runs are checked against
  independent recomputation of the counts, not against Lean.
- The log and snapshot numbering, which are not in the Lean state: Lean's `step`
  returns the state unchanged for a blocked step, while the interpreter appends a
  log entry and a snapshot.
- Declarations, data loading, outcome words, and explanations, which Lean does not
  model.
